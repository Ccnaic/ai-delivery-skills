# 并行派活（swarm）

**一句话：先切干净，再同时发，最后按统一格式收。**

> 为什么先切：并行的难点不在"同时跑"，在"切得开"。
> 切分有洞，并行只会让洞更大——因为没人看得见别人的活。

---

## 什么时候用 / 不用

**用**：
- 2 个以上任务，彼此不需要对方的产出
- 每个任务能独立判定"做完了"
- 没有共享文件、共享状态

**别用**：
- 任务之间相关（修 A 可能顺带修好 B）
- 需要看整体才能判断
- 会改同一批文件

> 实测：两个独立模块并行，**省 35% 时间**（58.8 分钟 → 37.9 分钟）。**但那是另一次实验，不是本流水线——见文末「有一组实测数据」。**
> 但波动从 6.6% 涨到 19%——**并行更快，但更不可预测**。

---

## Phase A：切（决定成败的一步）

派活之前必须先定三件事，**定不下来就别派**。

### A1. 定 done predicate

每个任务写一句：**"什么算做完了"**。

写不出可判定的句子，说明这个任务还没切好。

```
❌ "把主城做好"
✅ "主城场景能双击启动；有 5 个 NPC、3 个传送门；截图能看到这三样"
```

### A2. 选形状

| 形状 | 什么时候用 |
|---|---|
| **partition（切片）** | 任务能干净拆成几块，各做各的（主城 / 战斗 / 锻造） |
| **race（赛跑）** | 同一件事，让 N 个 worker 各做一版，挑最好的 |
| **混合** | 先切片，对不确定的片再赛跑 |

**用 race 必须提前声明怎么选**：取第一个过的（first pass）/ 全部排名（rank all）/ 取最好（best-of）。**不能等结果出来再定规则。**

### A3. 切域 + 给独立输出

**每个 worker 一个独立的工作目录，物理上不共享任何东西。**

```
run/m1/    ← worker 1
run/m2/    ← worker 2
run/m3/    ← worker 3
```

改同一个代码库时，用 git worktree（每人一个分支 + 一个工作区），最后合并。

### A3.5. 块之间有依赖怎么办（实测最容易翻车的地方）

真实任务里，"干净的独立块"很少。**命令层要调数据层、前端要调接口、战斗要用场景数据**——这不是"切得不好"，是任务本来的样子。

**做法：先冻结接口契约，再让各块独立实现。**

```
① 切完块，先标出谁依赖谁
   A 数据层  ←  B 命令层依赖它

② 把接口写成契约（函数签名 + 数据结构），写进一个文件
   Ledger.add(amount, category, note) -> dict
   Ledger.balance() -> {income, expense, balance, count}
   账本行格式：{"id","ts","amount","category","note"}

③ 下游块（B）只按契约编码，不读上游块（A）的实现
   → 这样 B 不会因为 A 改内部实现而崩

④ 契约本身算"共享状态"，但它只读、不改，不破坏隔离
```

**没有契约会怎样**：B 猜 A 的接口，A 后来改了，集成时全部重写。**这是分工最大的一种浪费，而且发生在最后一步，最难救。**

**契约写完要标一句**：`A3 的"零共享"在这里降级为"共享只读契约"`——这是有意偏离，不是偷懒，要让人看见。

### A4. 检查切分有没有洞

对着需求清单，逐条问：**"这条归谁？"**

归不上任何人的，就是洞。

> 实测教训：某次任务切成 6 个技术模块（数据/主城/战斗/锻造/建模/收口），每块都完成，但「符文」「镶嵌」不属于任何一块，**直接掉出去了**。
> 修法：切分之后，回查一遍需求条目，把无主的挑出来单独成块。

## Phase B：发（一条消息发完）

**所有 worker 在同一个响应里发出去 = 并行。一个响应发一个 = 串行。**

### 每个 brief 必须自包含

worker 是冷启动的，看不到你的上下文。少写一句，它就自己补一句。

```
必含五项：
1. 目标      这件事要达成什么
2. 范围      确切做哪一块，不做什么
3. 怎么验    做完怎么证明
4. 报告什么  回什么格式
5. 目录      在哪个目录干活，不许越界
```

### 统一报告格式

```
PASS      全部达成，附证据位置
ISSUES    有问题，列出能证明的全部问题（不是只报第一个）
BLOCKED   做不了，说明卡在哪
```

---

## Phase C：收（聚合规则）

### 三条硬规则

**① 没记录证据的，丢弃重跑一次**

worker 说 PASS 但没给证据位置 → 不算，重派一次。

**② 第二次还拿不出证据，记 gap**

**gap 不算 pass。** 缺结果就是缺，不能当"没消息就是好消息"。

**③ 覆盖检查**

- partition：每个片都必须有结果
- race：按 Phase A 声明的规则选

### 掉线处理

某个 worker 挂了 → **用 N-1 继续**，但报告里必须注明"少了哪个"。

---

## Phase D：出报告

一张表 + 一行问题 + 缺口说明。

```markdown
| 任务 | 结果 | 证据 | 备注 |
|---|---|---|---|
| 主城 | PASS | m1/SoronTowerTown.exe 可启动 | |
| 战斗 | ISSUES | m2/M2Combat.exe 可启动；Boss 只有 1 阶段 | 要求 3 阶段 |
| 锻造 | **gap** | 无输出（worker 超时） | 不计通过 |

**完成：2/3，1 个 gap**
```

**不要粘贴 worker 的原始输出**，只给结论和证据位置。

## 本环境的适配（重要）

### 载体：opencode 多进程

```bash
# worker 1（后台）
cd run/m1 && echo "" | opencode run --auto --model <model> "<把 brief 全文粘在这里>" &

# worker 2（后台，同一条消息里发）
cd run/m2 && echo "" | opencode run --auto --model <model> "<把 brief 全文粘在这里>" &
```

**注意 1**：`echo "" |` 不能省，否则 CLI 静默退出。

**注意 2（踩过）**：brief **必须内联进命令**，不要写成「读 TASK.md」。
之前这里写的是「读 TASK.md 并完成」，但全文从没说过要创建这个文件——照抄必失败（worker 报文件不存在）。

如果你更愿意用文件（brief 太长时值得），**必须先自己写出来**，且写成**绝对路径**：

```bash
# 派发前，每块各写一份
cat > run/m1/TASK.md <<'BRIEF'
<A3 的 brief 五项>
BRIEF

# 派发时用绝对路径，不要依赖 worker 的 cwd
cd run/m1 && echo "" | opencode run --auto --model <model> "读 $(pwd)/TASK.md 并完成" &
```

**判据**：不管用哪种，`ls run/mN/` 里能看到的文件，必须和命令行里引用的一致。

### 模型：统一，不按难度分

pstack 的做法是"最难的给最强模型，机械活给快模型"。**本环境用一个模型到底**，因为：
- 统一才好比较效果
- 免得搞混是"模型差异"还是"任务差异"

### 有一组实测数据（但不是本流水线的）

```
两个 worker 并行 vs 串行（同任务书、同模型、独立目录）

串行  58.8 分钟（两次：60.8 / 56.8）
并行  37.9 分钟（两次：34.7 / 41.2）
比值  0.644        省 35%

质量：8 个产物全部可启动，功能齐全
波动：串行 6.6%，并行 19%
```

**⚠️ 这组数据说明的是「并行派活本身能省时间」，不是「这套 swarm 流程能省 35%。」**

那次实验**没有用 recipe 的菜谱，也没有串 verify**。`切块 → 真并行 → verify` 这条完整链路**一次都没串过**。
所以 35% 只能当**量级参考**，不能当承诺。

**规划时按 35% 算，不要按 50% 算；但也别拿它当"这套流程已证明有效"的证据。**

## 常见坑

| 坑 | 后果 | 防法 |
|---|---|---|
| 切分有洞 | 某条需求没人做，且不会被发现 | A4：逐条问"这条归谁" |
| brief 不自包含 | worker 自己补设定，各做各的 | 五项齐全，缺一不发 |
| 没给独立目录 | 两个 worker 互相覆盖 | 一人一个目录 |
| 一个响应发一个 | 退化成串行 | 所有 dispatch 放同一响应 |
| 缺结果当通过 | 漏做但显示全绿 | gap 不算 pass |
| 并行超 2 个 | 资源竞争，收益递减 | 先测 2 个，超过再验 |
