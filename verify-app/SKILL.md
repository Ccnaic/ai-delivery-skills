# 给项目装一双眼睛（verify-app）

**一句话：让 AI 能真的跑起来、点下去、看见结果，而不是读代码猜。**

> 为什么需要：AI 读自己的代码，永远觉得没问题。
> 实测：某组写了 71 项自动化测试全过，人一玩——bug 一堆。
> 因为那些测试验的是逻辑，不是"跑起来是什么样"。

---

## 核心问题：AI 是瞎的

```
没有这层能力时：
  人 → 启动应用 → 操作 → 看结果 → 描述给 AI → AI 改 → 人再看
       ↑ 人就变成"人肉传送带"，连一个 agent 都跟不上

有了这层能力：
  AI → 启动 → 操作 → 截图 → 自己判断 → 自己改
       ↑ 人只在关键节点看一眼
```

**这一层是"信任 agent"的地基。** 没有它，其他所有流程都是纸上作业。

---

## 第一步：勘察（问代码，不问人）

**能从代码看出来的，不要问人。**

看不出来的，按顺序试：`README` → 配置文件 → 启动脚本 → 日志 → 跑一次看输出。

**还是没有 → 不问人，按最保守的假设做，并在 VERIFY.md 里写一行「这是假设」。**

理由：`deliver` 承诺过"范围确认后不再打扰用户"。为了搞清楚一个启动参数就去问，等于破坏这个承诺；而记一行假设，人不看也没损失。

### 五个必答项

| 项 | 问自己什么 |
|---|---|
| **Surface** | 用户实际碰的是什么？网页 / 命令行 / 桌面应用 / 游戏 / API？ |
| **Run** | 本地怎么启动？用项目自己的命令（package.json / Makefile / README），记下端口、环境变量、初始数据 |
| **Drive** | 怎么用程序去操作它？优先用已有的：Playwright、expect、curl、调试端口。都没有才自己写 |
| **Observe** | 能抓到什么证据？截图 / 终端输出 / 响应体 / 日志 / 退出码 / 数据库状态 |
| **Isolate** | 能不能同时跑两个实例？不能就明确写"禁止并行驱动"，比搞坏用户的会话强 |

### 如果项目本身跑不起来

**先修好（或精确报错），再生成验证工具。**

对着一个坏的基础写出来的验证工具，教给下一个 agent 的全是错的步骤。

---

## 第二步：生成验证工具

**两种交付形态，选一个。没说清会让人不知道该生成哪一种。**

| 形态 | 什么时候用 | 产出 |
|---|---|---|
| **轻 · 脚本** | 一次性任务、小项目、只想跑一遍 | 一个 `verify.py` / `verify.sh`，直接 `python verify.py` 就出结果 |
| **重 · 项目级 skill** | 会长期维护、多人接手、要反复验 | `.claude/skills/verify/`（或对应平台目录），含下面六节 + 功能地图 |

**两种形态内容要求一样**，区别只是"打包成文档给人读"还是"打包成脚本给人跑"。下面六节两种都要有——重形态写在文档里，轻形态写在脚本的注释和 `VERIFY.md` 里。

### ① Launch（启动）

```
- 确切的启动命令
- 怎么判断"真的就绪了"（某行日志、某个提示符）
- 就绪 = 可用，不是"进程还活着"
- 含 teardown（怎么关掉）
```

**注意**：数据库健康检查通过，不等于初始化脚本跑完了。

### ② Doctor（体检）

一个只读检查，回答"这个实例值得驱动吗"：

```
进程在不在 / 版本对不对 / 端口是不是我们的 / 认证有效没
```

**任何东西看起来不对劲时，agent 先跑这个。**

### ③ Drive（操作）

**用这个项目真实的路径和选择器**，不要写示例。

```
优先用稳定的把手：ARIA 标签、data 属性、命令名、路由路径
不要用：坐标、Tab 顺序
```

### ④ Evidence（证据）

**证据标准，五条硬规则：**

```
1. 走真实用户路径
   不许用内部 setter、测试专用端点、直接改数据库来"证明"功能可用

2. 捕获「动作 + 结果状态」
   不只是最终画面。要能看出"点了什么"→"发生了什么"

3. 同时验副作用
   写文件了吗？插行了吗？发消息了吗？

4. 只在生产边界已隔离的地方 mock
   别为了好测而把核心逻辑 mock 掉

5. 永远不要为了让流程通过而削弱流程
   ← 这条是防自欺的最后一道闸
```

### ⑤ Cleanup（清理）

```
- 只杀自己启动的进程，不许按进程名杀
- 清理实例和临时状态，但【不许删证据】
- 证据要留在一个技能里写明的固定位置
```

### ⑥ Helpers（辅助脚本）

**技能里带的脚本必须可执行，且调用方式写在正文里。**

> 需要读者反推怎么用的脚本，不算辅助脚本。

---

## 第三步：功能地图

给每个用户能碰到的功能建一个文件（先做 3–5 个主要的）。

每个文件回答四个问题：

```markdown
## 子功能
这个功能包含哪几块

## 用户怎么到达（用户视角）
从哪进、按什么、需要什么前置

## 怎么用工具驱动它
具体命令 / 选择器

## 坑
已知的陷阱、需要的初始数据
```

**地图是项目的验证基准。** 只驱动一个方便入口的"证明"是不完整的——地图上列了别的，就得覆盖。

**如果初始数据缺了某个前置条件，那次验证就报失败，原因写进「坑」。永远不要削弱流程让它通过。**

---

## 第四步：自证（必须做）

**生成完，自己按它的说明完整跑一遍：**

```
启动 → 体检 → 驱动一个功能 → 截取证据 → 清理 → 确认证据还在
```

**最后一步最容易被忽略**：清理脚本把证据一起删了，等于白跑。

> **一个从未被执行过的生成技能，是草稿，不是交付物。**

如果是在"替身环境"里验的（容器代替真机、本地栈代替远程），**必须列出替身做了而真机不会做的所有步骤**——那些步骤在真机上跑过之前，都算未验证。

---

## 针对不同类型应用的具体做法

### 网页 / Electron

```
驱动    Chrome DevTools Protocol（CDP）
        启动、截图、点元素、读 console
证据    截图 + DOM 快照 + 网络请求
```

### 桌面应用（含游戏）

```
驱动    启动 exe → 模拟键鼠（pyautogui 之类）→ 截图
        或者：游戏内建一个 --autotest 参数，跑内置测试
证据    截图（全屏）+ 日志文件 + 进程存活时长
```

**游戏类的三个必测**（普通测试覆盖不到的）：

```
1. 能不能启动        双击 exe，10 秒内有画面
2. 关键路径走不走得通  从起点能不能走到目标（不是"目标存在"，是"走得到"）
3. 平衡性           不按键打一只怪要多久？会不会秒死？
```

第三条最容易漏，也最容易毁掉体验。

### 命令行 / TUI

```
驱动    Linux/macOS：tmux 会话或 PTY
        Windows：subprocess 管道（没有 tmux，别硬套）
证据    终端转录 + 退出码
```

**Windows 下必须做的三件事**（实测踩过）：

1. **强制 UTF-8**：`python -X utf8 script.py`，否则子进程中文输出解码会崩
2. **别用 tmux**：Windows 没有，用 `subprocess.run(capture_output=True)` 等价替代
3. **用 `-I` 验证零依赖**：`python -I` 隔离环境，能跑说明没用第三方库

**证据要捕获"动作 + 结果状态"两部分**：不只记最终输出，还要记每条命令的 `exit code` 和它对文件的副作用（账本多了几行、配置改了哪个键）。

### 服务 / API

```
驱动    curl / HTTP 客户端
证据    响应体 + 状态码 + 数据库状态
```

## 常见坑

| 坑 | 后果 | 防法 |
|---|---|---|
| 只验"存在"不验"可达" | 目标在那儿，但走不过去 | 加"走一遍"的测试 |
| 用内部接口"证明"功能可用 | 用户那条路上其实是坏的 | 必须走真实用户路径 |
| 断言恒真 | 功能坏了也 PASS | 问"如果它全坏，这条还会过吗" |
| 清理把证据删了 | 白跑 | 清理后确认证据还在 |
| 生成完不跑 | 交的是草稿 | 必须自证一次 |
| 替身环境验完就当真的 | 真机上失败 | 列出替身多做的步骤 |

---

## 一句话

> **能自己看见结果的 agent，才配拥有更大的自主权。**
> 看不见的，只能靠人盯着——那就不叫自动化，叫遥控。
