# deliver：把四个 skill 连成一条流水线

**本文件只做编排，不重复其他 skill 的内容。** 每一步都要去读对应的 SKILL.md，不要凭记忆。

```
recipe       怎么问、怎么写菜谱、怎么打勾
swarm        怎么定标准、怎么切块、怎么查洞
verify-app   怎么生成验证工具、怎么证明真的能跑
encode-lessons  怎么把错误变成规则
```

---

## 第 0 步：要不要用（30 秒，必须真判断）

**这一步的意义是：不让小任务被重流程拖慢。** 之前 16KB 的协议就是这么废掉的——管四个模块的活，配了一套航空级质量体系。

逐个回答，**命中任意一条即够格**：

| # | 问句 | 命中的样子 |
|---|---|---|
| 1 | 需求描述里有主观词、数量词没定、或涉及取舍？ | "做好点""尽量还原""看着办""要几个"没答案 |
| 2 | 预估超过 30 分钟 / 多个模块 / 要交文件？ | 不是一次性问答，是要产出东西 |
| 3 | 做错了要返工、要给人用、要发布？ | 交付给别人、上生产、客户要用 |
| 4 | 同类任务曾经漏做过？ | 有前科（"上次那个就漏了"） |

**四条全不中 → 直接做，不加载任何流程。**

但交付时仍要说一句：**做了什么、没做什么。** 这一句是免费的。

---

## 第 1 步：选档

| 档 | 条件 | 走哪几步 |
|---|---|---|
| **轻档** | 需求清楚（第 1 条不命中），但第 2/3/4 条命中 | 做 → `verify-app` → 逐条打勾 |
| **重档** | 第 1 条命中（需求模糊），或"大且复杂" | `recipe` 问 → 菜谱 → `swarm` 切 → 做 → `verify-app` → 逐条打勾 |

**判定不清就选重档**——多做一步的成本，远低于漏做一片的成本。

---

## 第 2 步：走

### 轻档

1. 做（不用菜谱，但要先扫一遍原话里的**数量词、否定词、专有名词**，这三类最容易在转述中丢）
2. 调 `verify-app`：生成验证工具，**真的跑一遍**
3. 调 `recipe` 第四步：按原话逐条打勾，报 N/M

### 重档

```
【人工】1. 完整读 recipe → 问 8 个问题 → 追问到清楚 → 写菜谱
        2. 复述确认（含「我假设的」逐条列出）→ 声明自动区间
────────────────── 用户说"对"，以下全自动 ──────────────────
        3. 过 G1（机械检查）
        4. 完整读 swarm → 定 done predicate → 切域 → 过 G2
        5. 执行。能起多进程就并行，起不了就串行
           —— 但切块和 A4 回查照做（切块本身有价值，不只是为了并行）
        6. 调 verify-app：生成验证工具，真的跑一遍 → 过 G3
        7. 按原话逐条打勾 → 过 G4
        8. 写 DELIVERY.md，交付
```

**只有第 1–2 步需要人，第 3–8 步不问任何人。**

### 自动区间声明（在复述确认后立刻说）

```
范围已锁定，接下来从拆解到交付不再打扰你。
中途只有两种会找你：① 需要你拍板的取舍 ② 彻底做不下去了。
交付时一次报 N/M。
```

**说这句话的意义是让人可以走开。** 不说，用户会一直守着怕它卡住。

---

## 四道闸门

**四道闸门都「不问人」，只做检查。** 检查不通过的后果，落在**交付物**上（降级成 ❌、记进 DELIVERY.md），而不是停下来等人。

| 闸门 | 卡什么 | 不通过会怎样 |
|---|---|---|
| **G1** | 每行范围决策有没有标来源 | 自己补标；补不了 → 标「AI 假设」，交付时降级结论 |
| **G2** | 切块后有没有无主需求 | 必须单独成块；没成块就记进 DELIVERY.md 的「没验的」 |
| **G3** | 验证有没有真的跑过 | 没跑 → 这一块不许打 ✅，只能打 ⚠️ |
| **G4** | 打勾有没有证据 | 没证据 → 降级成 ❌ |

**唯一的人工点是 `recipe` 第三步的复述确认。除此之外，从拆解到交付不问任何人。**

### G1 · 范围确认（机械检查，不再问人）

**人工确认在 `recipe` 第三步已经做完了。这一关只查格式，不停下来问人。**

| 情况 | 动作 |
|---|---|
| 每一行都有来源（「人」或「AI 假设」） | 过 |
| 有空行没标来源 | **回去补标**，补完再过 |
| 出现「AI 假设」 | 过，但交付时必须降级结论（见「没人在场」一节） |
| 有【待定】且它卡住整个任务 | 属于"需要你拍板的取舍"，可以问一次——但这已经写在自动区间声明里了，不算额外打扰 |

**这一关防的是**：AI 写菜谱时悄悄把一个空格填掉，当成人定的事实。

**为什么不能省**：范围是分母。分母错了，后面所有执行、验证、清点，全在量一个错的东西，而且做得越好越浪费。

**为什么不再问人**：同一个信息问两遍会让人烦。所有假设已经在复述那一次逐条列出、一次确认完了。人工点只有一个，放在最值钱的位置。

### G2 · 切块无洞（警告 + 记录）

`swarm` 的 A4 回查结果：每条需求都有归属吗？

无主的需求 → **必须单独成块**，不许"之后再补"。

### G3 · 验证真跑过（警告 + 记录）

`verify-app` 的产物**必须真的执行过一次**，有输出、有退出码。

只看代码没跑 → **不许打勾**。

> 一个从未被执行过的验证工具，是草稿，不是交付物。

### G4 · 打勾有证据（警告 + 记录）

N/M 里每个 ✅，都要指向一个证据：文件名、日志行、命令输出、截图。

**找不到证据的，降级成 ❌。** 不许"我记得做了"。

## 失败库（可选，但强烈建议）

四条闸门里任一条**拦下了东西**，就在 `failures.md` 记一行：

```
| 日期 | 哪道闸门 | 拦下了什么 | 下次怎么避免 |
```

同一个错犯到第三次，调 `encode-lessons`，把它变成结构约束（lint 规则、目录边界、检查脚本），让它**物理上不可能再犯**。

---

## 没人在场时怎么办（降级规则）

自动化跑、测试跑、用户只说"你看着办"——G1 会被人绕过。这时**不许假装有人确认过**：

1. 范围决策照填，但每行标 `AI 假设（无人在场）`
2. 交付时把结论降级，明写：
   ```
   ✅ 5/5 完成 —— 但分母是 AI 假设的，若你要的是 7 层，实际是 3/7
   ```
3. 单独列一节「我假设的范围」，方便人一眼扫完就纠正
4. 有把握说"我不确定要几层"，也不许悄悄定一个数当事实

## 交付时必须有的一份东西

在项目根写 `DELIVERY.md`，一页，四块：

```markdown
## 档位
重档（命中标准 1：需求模糊）

## 闸门
G1 范围确认   ✅ 6 行全部标来源，其中 1 行标 AI 假设
G2 切块无洞   ✅ 回查 12 条需求，4 条无主 → 已单独成块 C
G3 验证真跑   ✅ verify.py 20/20 PASS，exit 0（evidence/verify_211041.txt）
G4 打勾有据   ✅ 5/5，每项有证据

## 跳过的步骤
skip: 变异测试 —— 任务太小，判据只有 3 条，破坏测试成本不划算

## 没验的
界面顺眼 / 提示语习惯 / 长期手感 —— 只能人真的用一次
```

**这一页就是"这套流程跑过"的唯一证据。** 没有它，等于没走。

---

## 一句话

> **先判断要不要用（防流程压垮小任务），再分档（防大任务走得太轻），四道闸门卡住四种失败：范围没确认、切块有洞、没跑说过、打勾无据。**

---

## 边界

| 能防 | 不能防 |
|---|---|
| 范围被悄悄缩小 | 做出来了但不好玩 |
| 切块切掉需求 | 模型能力不足 |
| 验证器假通过 | 需求本身写得不清楚 |
| 打勾没证据 | 审美判断 |

**质量问不出来，只能看出来。** 甲方第一次看到东西才知道"不对"，所以做完一小块就先给他看，不要憋到最后。
