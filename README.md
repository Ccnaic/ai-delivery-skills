# 五个 skill：一个入口 + 四件工具

> **状态：beta。** 可以用，但只跑过一次，规模偏小。下面「验证到什么程度」一节写清了哪些验过、哪些没验——**用之前先读那一节**。

一套轻量的需求落地流程。**不依赖多 agent、不依赖特定平台、纯 Markdown。**

---

## 它们解决什么问题

AI 最典型的失败不是"做错"，是**把范围悄悄做小，然后在缩小的范围里做到极致**。

实测过：让它"还原一个游戏"，它只做了 1/3 层数，然后用 5000 行代码把那一层做得很好——全程没人问过"一共要做几层"。

五个 skill：**一个负责判断和编排，四个负责做事**。

| skill | 角色 | 防什么 |
|---|---|---|
| **deliver** | **入口 / 编排** | 小任务被重流程拖慢；大任务被草率处理 |
| **recipe** | 工具 | 范围被悄悄缩小 |
| **swarm** | 工具 | 活分下去有洞 |
| **verify-app** | 工具 | AI 瞎做，看不见结果 |
| **encode-lessons** | 工具 | 同样的错反复犯 |

## 怎么串

```
任务下达
   ↓
deliver 第 0 步：够格判断（四条，命中任一才继续）
   │
   ├─ 都不中 → 直接做，只报"做了什么/没做什么"（不加载流程）
   │
   └─ 命中 → 选档
        ├─ 轻档：做 → verify-app → 逐条打勾
        └─ 重档：
             【人工】问 8 个问题 → 追问到清楚 → 写菜谱 → 复述确认
            ─────────── 用户说"对"，以下全自动 ───────────
             [G1] → swarm 切 → [G2] → 做 → verify-app → [G3]
                  → 逐条打勾 → [G4] → 写 DELIVERY.md → 交付
```

**全程只有一次人工确认**（复述那一次，含"我假设的"逐条列出）。确认完会明确宣布自动区间，人可以直接走开。

**四道闸门是"连起来"的关键**——都只做检查、不问人，检查不通过的后果落在交付物上：

| 闸门 | 卡什么 | 不通过会怎样 |
|---|---|---|
| **G1** | 范围决策每行有没有标来源 | 自己补标；补不了 → 标「AI 假设」，交付时降级结论 |
| **G2** | 切块后有没有无主需求 | 必须单独成块，否则记进「没验的」 |
| **G3** | 验证有没有真的跑过 | 没跑 → 该块不许打 ✅ |
| **G4** | 打勾有没有证据 | 没证据 → 降级成 ❌ |

## 怎么装

### 方式一：克隆后复制（推荐）

```bash
git clone https://github.com/<你的用户名>/ai-delivery-skills.git
```

然后按你的 agent 复制对应目录：

```
<repo>/deliver/  recipe/  swarm/  verify-app/  encode-lessons/
   ↓
.claude/skills/<name>/SKILL.md       → Claude Code
.workbuddy/skills/<name>/SKILL.md    → WorkBuddy（需重启会话）
.opencode/skills/<name>/SKILL.md     → opencode
```

每个 skill 目录里只有一个 `SKILL.md`，**自包含，不用改任何路径**。

### 方式二：只拷你需要的那几个

五个 skill 互相不依赖，单独用也行：

| 只想要 | 拷贝这个目录 |
|---|---|
| 把需求问清楚 | `recipe/` |
| 并行派活 | `swarm/` |
| 给项目加验证 | `verify-app/` |
| 把错误变成规则 | `encode-lessons/` |
| 全流程总控 | `deliver/`（会调用上面四个） |

### WorkBuddy 用户注意

实测这个环境**只扫描用户级** `~/.workbuddy/skills/`，项目级 `.workbuddy/skills/` 放了几天从没被加载过。

所以装完要复制到用户级目录。仓库里的 `sync.sh` 是给"项目级当源、用户级当安装副本"这种维护方式用的：

```bash
cd .workbuddy/skills
./sync.sh --dry-run   # 先看会改什么
./sync.sh             # 真同步（旧版自动备份成 .bak_时间戳）
```

**复制或同步完都要新开一个会话才生效**——技能清单是会话启动时生成的。

## 三个硬性设计原则

**① 范围决策必须由人拍**

"做几个 / 几层 / 什么不做"这几个空，AI 不许填。因为这是分母，分母错了后面全在量错的东西。

**② 统计只能按用户原话，不许按技术模块**

实测教训：任务被切成 6 个技术模块，每块都完成了，但「符文」「镶嵌」不属于任何一块，直接掉出去——**按模块统计显示全绿，按原话统计才会暴露**。

**③ 断言必须能被打败**

每写完一条判据就问：**如果功能全坏，这条还会 PASS 吗？** 会 PASS 的，是假判据，重写。

---

## 一个实测数据

并行的收益（两个独立模块，同任务书、同模型、独立目录）：

```
串行  58.8 分钟
并行  37.9 分钟
节省  35%    （比值 0.644）

但波动：串行 6.6%，并行 19%
```

**结论：并行值得做，但按 35% 规划，别按 50%。**

## 验证到什么程度（重要，别当成稳定版）

**跑过一次全链，2026-11-08，13 分钟。**

```
任务：「做一个命令行记账工具，能记一笔、查余额、看记录。做得实用点。」
规模：749 行 Python / 18 个文件
模型：deepseek-v4.1-flash（单进程 opencode，无法真并行）
```

### 验过的

| 环节 | 产出 | 是否起效 |
|---|---|---|
| recipe | 8 问 + 菜谱 + 复述 | ✅ 范围决策逐项标了来源，并标注"全部是代答" |
| swarm A4 | 逐条回查"这条归谁" | ✅ **真的抓出 4 条无主需求**（默认路径/根入口/README/验证脚本），单独成块 |
| verify-app | `verify.py`，20 项检查 | ✅ 独立复跑：**20/20 PASS，exit 0** |
| 变异测试 | 把 `balance()` 改成恒 0 | ✅ 真的改了代码，verify 变成 **19/20，exit 1**，抓到那条 FAIL |
| recipe 第四步 | 原话逐条打勾 | ✅ 5/5，且列明"未验证：界面顺眼、提示语习惯、长期手感" |

那次运行还抓出两个真实产品 bug：月份校验被跳过、收入金额少正号。

### **没验过的**（用之前必须知道）

| 没验 | 为什么重要 |
|---|---|
| **真实规模任务** | 749 行是那个失败案例的 1/7。**任务不够大，agent 根本不需要取舍，"悄悄缩小范围"这种失败就不会发生**——也就是说，它要防的病，这次没机会出现 |
| **真人在场** | 8 个问题是 agent 自己扮演用户答的。**recipe 的核心机制（人拍分母）从未真正跑过**，5/5 的分母是 AI 自己定的 |
| **并行串联** | 35% 那个数字来自另一个实验，**没用上 recipe/swarm**。`切块 → 真并行 → verify` 这条链一次都没串过 |
| **GUI / 游戏路径** | verify 只测了命令行。最难的「启动窗口、点按钮、截图判断」未验 |
| **encode-lessons** | 零测试（要"同一个错犯三次"才触发，单次任务碰不到） |
| **deliver** | 就是上面那次测试之后才写的。**它一次都没跑过**——四道闸门能不能真的拦住东西，没验 |
| **重复性** | n=1。换任务、换模型会不会一样，不知道 |

### 一句话

> **能抓漏（A4 验过）、能打败断言（变异测试验过），但"能不能在真实大任务上防住范围缩小"这件事，还没测。**

## 这次测试暴露的 15 处问题，修了 3 处

（完整清单见 `examples/PROBLEMS.md`）

| 问题 | 修法 |
|---|---|
| 无真人时，"范围必须人拍"必然被绕过 | recipe 补「没有真人时怎么办」：允许代答，但每个数字标来源，交付时降级结论 |
| 块之间有依赖时，"零共享"是假话 | swarm 补 A3.5：先冻结接口契约，下游只按契约编码 |
| "生成项目级 skill"和"生成脚本"两种说法不一致 | verify-app 补两种交付形态（重/轻），六节内容两者都要有 |

## 边界

| 能防 | 不能防 |
|---|---|
| 范围被悄悄缩小 | 做出来了但不好玩 |
| 漏做（以为做完了） | 模型能力不足 |
| 验证器失效（假通过） | 需求本身写得不清楚 |
| | 审美判断 |

**质量问不出来，只能看出来。** 所以 `recipe` 的最后一条建议是：访谈结束后先做个粗糙的小样，给他看，他说哪里不对，再正式开工。
