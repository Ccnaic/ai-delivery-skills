# 需求菜谱

**一句话：先把"要什么"写成一张表，再动手；交付时按这张表逐条打勾。**

> 为什么需要它：AI 最常见的失败不是"做错"，是**把范围悄悄做小，然后在缩小的范围里做到极致**。
> 实测案例：让 AI"还原一个游戏"，它只做了 1/3 的层数，然后用 5000 行代码把那一层做得很好。
> 全程没人问过它"一共要做几层"。

---

## 什么时候用

- 任务里有「尽量」「差不多」「像 XX 那样」「做好看点」「要专业」这类词
- 用户说"我想做个 X"，但没说做几个、做什么、不做什么
- 你已经问过一轮，答案还是模糊的

**别用的时候**：任务已经具体到输入输出、数量、验收标准都清楚。直接做。

---

## 第一步：问（8 问，开放式）

**问法要求**：开放式，不带 ABCD 选项。答不上来时用下面的「提问技巧」换角度。

| # | 问什么 | 为什么问 |
|---|---|---|
| 1 | 这东西做出来给谁用？解决他什么问题？ | 定场景，才知道什么该做、什么多余 |
| 2 | **你最想要的是什么？说三个。** | 正面需求 |
| 3 | **你最不能接受的是什么？说三个。** | 反面需求，往往比第 2 问好答，也更能定边界 |
| 4 | 如果只能保住一样，保哪个？ | 逼出核心，决定后面所有取舍 |
| 5 | 有没有参照物？你用过、玩过、看过的东西 | 参照物比形容词准一百倍 |
| 6 | 明确不做什么？ | 能省掉一半返工 |
| 7 | 数量级是多少？几个 / 几层 / 几种 / 多长？ | **这是分母**，没有它没法验收 |
| 8 | 什么时候要？能花多久？ | 决定后面问多细 |

> 第 5 问是关键：「像 XX 那样」一句话，胜过十句「要专业、要现代、要简洁」。

---

## 提问技巧（解决"词汇匮乏"）

### 技巧一：用场景代替术语

用户不懂术语，但一定懂自己的生活。

| 术语型（❌） | 场景型（✅） |
|---|---|
| 你要什么战斗系统？ | 打架时你希望手忙脚乱一直按，还是能停下来想想？ |
| 美术要什么风格？ | 截图发到群里，你希望别人说"这什么游戏"还是"这画面好土"？ |
| 要什么架构？ | 以后想改的话，你希望改一个地方还是十个地方？ |

### 技巧二：给示例，不给选项

不列 ABCD，而是说：

> 「比如有人会答『我要三档品质』，但这只是例子，不是标准答案。」

**示例是锚点，选项是笼子。用前者。**

### 技巧三：答不上来就换角度（同一件事问三次）

```
第一遍  场景 →  "你希望用起来是什么感觉？"
第二遍  对比 →  "A 方案和 B 方案，哪个更接近？为什么？"
第三遍  排除 →  "那我们先假设不做这个，你会觉得少了什么？"
```

**三次问不出来，说明用户自己也没想清**——标【待定】，**不要替用户编答案**。

---

## 第一步之后：追问到清楚（必做）

**问完 8 个问题不等于问清楚了。** 这一节定的是"什么时候算问够了"。

### 一、什么叫"清楚"（四条判据，满足任一条即算）

| # | 判据 | 例子 |
|---|---|---|
| 1 | **有数字** | 「3 层」「7 孔」「5 种怪」「不超过 200 行」 |
| 2 | **有明确边界** | 「不做联机」「8 层以后不做」「只用标准库」 |
| 3 | **有可查的真值来源** | 「照 Forge 配置那九档」「按上次那个页面的布局」 |
| 4 | **有可观测的行为** | 「不按键也一直在打」「点一下出结果，不等 3 秒」 |

**四条都不满足 = 不清楚，必须追问。**

四不靠的典型回答（**全部要追**）：`要专业` `做好看点` `尽量还原` `内容多一点` `你看着办`

### 二、四把刀（按顺序试）

| # | 刀 | 问法 |
|---|---|---|
| ① | **逼数字** | 「大概几个？3 个够吗？5 个要不要？」 |
| ② | **逼边界** | 「那 XX 算不算在里面？」 |
| ③ | **逼反例** | 「什么样的情况下你会说『这不是我要的』？」 |
| ④ | **逼取舍** | 「如果只能保一样，保哪个？」 |

**逼数字永远排第一**——分母就是数量，而数量最容易被「差不多」「看情况」糊过去。

配合上面的「技巧三：换角度」：**四把刀是四种问法，换角度是同一把刀换三次说法。**

### 三、什么时候停

```
满足四条判据之一        → 停，写进菜谱
四把刀 × 换角度都试过   → 停，标【AI 假设】或【待定】
```

第二种情况下**不许再问**。理由：

> 用户真不知道的时候，硬问出来的数字一定是编的，最后一定错。
> 宁可标一个假设、在复述时让人看见，也不要逼出一个假答案。

**「问到清楚为止」的边界是：问到清楚，不是问到用户烦。**

### 四、一轮之后的覆盖检查（最容易漏，必做）

8 问结束，对着菜谱的 5 个范围决策栏**逐格看**：

| 栏 | 状态 | 动作 |
|---|---|---|
| 做几个 / 几层 / 几种 | ✅ 有数字 3 层 | 过 |
| 必须要的 | ✅ | 过 |
| 明确不做的 | ❌ 空着 | **专门追问这一格** |
| 精度要求 | ❌ 空着 | **专门追问这一格** |
| 预算 | ✅ | 过 |

**空着的格子，要么追问，要么标成【AI 假设】，不许静默填掉。**

> 实测教训：AI 把「还原所有内容」自己理解成「做 1 层就行」，然后用 5,000 行代码把那一层做到极致。**那个空格从头到尾没人填过。**

### 五、保留追问记录

写进菜谱，避免同一件事问两遍：

```markdown
## 追问记录
| # | 问过什么 | 得到什么 | 停在哪 |
|---|---|---|---|
| 1 | 「几层？」→「看情况」→「3 个够吗？」 | 3 层 | 有数字 |
| 2 | 「精度要多少」×3 + 换角度 | 未定 | 标【AI 假设】 |
```

## 第二步：写菜谱

问完就写成下面这张表。**这是整个流程的核心产出。**

```markdown
# 菜谱：<项目名>

## 一句话
<做什么，给谁用>

## 范围决策（这些数字锁死，中途改要重开）
| 项 | 决定 | 谁定的 |
|---|---|---|
| 做几个 / 几层 / 几种 | | 人 |
| 必须要的 | | 人 |
| 明确不做的 | | 人 |
| 精度要求 | | 人 |
| 预算 | | 人 |

## 执行条目（AI 拆）
| # | 用户原话（逐字） | 要做到什么 | 真值来源 | 怎么验 |
|---|---|---|---|---|
| 1 | | | | |
| 2 | | | | |

## 待定项（用户自己也没想清的）
| # | 问题 | 处置 |
|---|---|---|
```

### 关键：范围决策必须由人拍

**AI 不许填「范围决策」这五个空。**

这是整套流程里最重要的一条。因为：

```
范围决策 = 分母
分母错了 → 后面所有执行、验证、清点，全在量一个错的东西
```

实测案例：AI 自己把"还原所有内容"理解成"做 1 层就行"，然后完美地完成了 1 层。**没人发现少了 2/3。**

### 没有真人时怎么办（重要）

自动化跑、测试跑、用户只说"你看着办"的时候，人拍这一环会被绕过。这时**不许假装有人拍过**，按这三步降级：

1. **照常拆、照常填，但每个数字都标来源**
   ```
   | 做几个 | 3 层 | 人（Q7 回答）      ← 真的问到了
   | 做几个 | 3 层 | AI 假设（无人在场） ← 自己填的
   ```

2. **交付时把结论降级**，明写"范围未经确认"
   ```
   ✅ 5/5 完成 —— 但分母是 AI 假设的，若你要的是 7 层，实际是 3/7
   ```

3. **范围假设单独列成一节**，方便人一眼扫完就纠正
   ```
   ## 我假设的范围（请确认或改）
   - 层数 3（你没说，我按 1 小时预算估的）
   - 不做联机（你没说，我按单机估的）
   ```

**为什么不能省这一步**：范围假设是唯一"错了就全盘皆错"的地方。产出做得再好，分母错了等于零。**宁可交付时说"我不确定要几层"，也不许悄悄定一个数然后当作事实。**

## 第三步：复述确认（全程唯一的人工点）

把菜谱复述给用户，**等他说"对"再动手**。

**这一下确认完，后面到交付不再问他任何问题。**

```
我理解你要的是：

做什么：<一句话>
范围：<具体数量>
必须要：<列出>
明确不做：<列出>
怎么算做好了：<列 3 条能观测的>
预算：<时间>

⚠️ 这几条你没说，我自己假设的（有异议现在说）：
  · <假设 1>（标：AI 假设）
  · <假设 2>（标：AI 假设）

对吗？哪里要改？
```

**必须包含「我假设的」这一段。** 如果全是你答的，就写「以上全部来自你的回答，我没有假设」。

用户回「对」之后，紧接着说一句**自动区间声明**：

```
范围已锁定，接下来从拆解到交付不再打扰你。
中途只有两种会找你：① 需要你拍板的取舍 ② 彻底做不下去了。
交付时一次报 N/M。
```

### 为什么假设必须在这里一次确认完

如果留到后面再确认，就会出现**同一个信息问两遍**：复述时问一次，开工前又因为"发现 AI 假设"再问一次。

**人工点越少越好，但必须放在最值钱的位置**——范围是分母，分母只能由人定。所以：**只在这一处停，别在别处再停。**

---

## 第四步：交付时逐条打勾

交付前，按**用户原话**逐条打勾，报 N/M。

```markdown
| # | 用户原话 | 状态 | 证据在哪 |
|---|---|---|---|
| 1 | 所有内容和玩法 | ⚠️ 层数只做了 1/3 | scripts/ 无 F2/F3 |
| 2 | 不要像素风 | ✅ | screenshots/01.png |
| 3 | 魔塔层数 ≥3 | ❌ 只做了第一层 | 代码 grep：第一层×18 |

**计数：1 完成 / 1 部分 / 1 未做（合计 3）**
```

### 两条硬规则

**① 必须写成 N/M 的数字**，不接受"我核对过了""基本完成"

**② 只能按用户原话统计，不许按技术模块统计**

这一条来自实测：某次任务被切成 6 个技术模块（数据/主城/战斗/锻造/建模/收口），每块都完成了，但「符文」「镶嵌」不属于任何一块，直接掉出去——**按模块统计会显示全绿，按原话统计才会暴露缺口。**

### 缩范围可以，但必须写出来

```
悄悄缩（交付时不说）  → 失败
明说"这条没做"        → 及格
```

---

## 附则：失效判据（可选，但强烈建议）

每写完一条判据，问一句：

```
如果这个功能完全坏掉 / 被删掉 / 被改成 return true，
这条判据还会 PASS 吗？
```

- **会 FAIL** → 判据有效
- **仍然 PASS** → **判据无效，重写**

### 五种已被验证的无效形态

| 形态 | 实例 | 为什么无效 |
|---|---|---|
| 查名称不查结果 | 文件改名后仍 PASS | 缓存还在，断言的只是"有个东西叫这名" |
| 正则子串匹配 | `##\s*键位` 会命中 `### 键位` | 标题降级一级也照样通过 |
| 读数不可区分 | 测距离用 `0.00 米` | 塞墙里也是 0.00 |
| 恒真断言 | `sum == 32.000 == maxHP` | 代数恒等，功能全坏也是 32 |
| 单次绿 | 80% 成功率只跑一次 | 概率上不构成证明 |

> 最后一条补充：**判据写完了要真的去破坏一次**，只看表格里写"如果坏了会 FAIL"不算数。实测里有一组写了这句话但从未真的破坏验证，等于没做。

---

## 四条硬规则（总）

1. **追问到清楚才算问完。** 答案必须满足四条判据之一：有数字 / 有边界 / 有真值来源 / 有可观测行为。
2. **假设必须在复述里一次列完。** 确认完就全自动，同一个信息不许问第二遍。
3. **答不上来的标【待定】或【AI 假设】，不许替用户编。** 编出来的数字，最后一定会错。
4. **统计口径按原话，不按模块。** 按模块统计，必漏"不归属任何模块"的需求。

---

## 常见坑

| 坑 | 后果 | 怎么防 |
|---|---|---|
| 用户说"你看着办" | AI 自己填范围，最后不符 | 不接这个答案，改成"那我先按 X 做，不对你喊停" |
| 用户答"越多越好" | 没有分母，永远做不完 | 逼数字：「10 个够吗？20 个要不要？」 |
| 用户答"要专业" | 无法判定 | 改问：「什么叫专业？给我一个你觉得专业的例子」 |
| **四把刀试完还在追问** | **把人问烦，访谈中断** | **停，标【AI 假设】，进复述让他看见** |
| 问太多把人问跑 | 访谈中断 | 必答层只 8 问，其余按回答深入 |
| 访谈完直接开工 | 理解有偏差，全盘返工 | 必须复述 + 确认 |
| 复述时漏说假设 | 后面又要问一遍 | 复述模板里必须有「我假设的」这一段 |

---

## 这份 skill 的边界

| 能防 | 不能防 |
|---|---|
| 悄悄缩小范围 | 做出来了但不好玩 |
| 漏做（以为做完了） | 模型能力不足 |
| 验证器失效（假通过） | 需求本身写得不清楚 |
| | 审美判断 |

**质量问不出来，只能看出来。** 所以访谈结束后，建议先做一个粗糙的小样给他看，他说哪里不对，再正式开工。
